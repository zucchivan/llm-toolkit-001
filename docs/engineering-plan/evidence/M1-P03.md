## Durable lifecycle / recovery table (written before implementation; amended 2026-11-26)

| Durable phase | Observed resource | Allowed next action | Forbidden action |
| --- | --- | --- | --- |
| `intent` committed; no cgroup observed | Host-owned durable lease journal keyed by one fresh lease UUID; no cgroup child required to exist yet | On reopen, inspect only the exact UUID-derived child; if absent, record terminal `not-launched`/recovery result and permit a new fresh UUID after receipt | Launch before intent commit; infer launch from a guest manifest; reuse this UUID for another child |
| `cgroup-created`; launch not recorded | Exact child path under the delegated cgroup parent; `cgroup.events`, `cgroup.procs`, `cgroup.kill` | Launch trusted bwrap through an already-opened child cgroup `cgroup.procs` placement gate; record launching state before bwrap can execute project code | Spawn project code outside the child; accept a PID-only fence; delete/reuse the cgroup while state is uncertain |
| `launching`; no trusted acknowledgement | Exact cgroup identity plus bounded control stream and launcher process identity; guest claims are untrusted | On reopen/timeout/controller death, write `1` to this exact `cgroup.kill`, wait for `populated 0`, then mark fenced; if unavailable remain recovery-required | Treat helper hello, guest manifest, pidfd/PID exit, or bwrap exit alone as proof all descendants are dead; import |
| `attached`; guest may be running | Same exact cgroup plus trusted helper handshake bound to lease UUID/role; namespace checks performed inside launched namespace | Exchange fixed protocol frames; on any uncertain transport or owner loss, kill and verify empty before later recovery | Accept a guest-supplied cgroup/fence claim; launch a second workload in the lease; use workload stdio as control channel |
| `fencing`; kill requested, not yet empty | Exact cgroup `cgroup.events` reports `populated 1` or cannot be read | Retry only the same kill/observation against the same child; remain recovery-required if capability/identity is lost | Import, remove child, replace child identity, declare success on timeout |
| `fenced`; `populated 0` verified | Exact cgroup identity and durable fence observation; no guest writer remains | Exclude all writers/reattachment, scan the full fenced projection with bounded no-follow reads, construct and durably stage the host-owned sealed result; record import intent only after sealing | Trust guest fence booleans; read mutable guest paths; import before the empty-population observation |
| `importing`; fence verified; no import receipt | Host-owned durable sealed content bound to lease/base/controls/projection and recorded destination/result identity; destination still private/unpublished | Revalidate all names/types/modes/limits/digests and atomically commit the complete validated delta; on crash re-open only the same sealed bytes or retain recovery-required | Partial import; arbitrary tar extraction; follow links; change destination; treat missing receipt as rollback |
| `imported`; result receipt not committed | Host-owned imported delta/digest and durable fence | Reconcile the same import by digest and write the missing result receipt; identical replay is idempotent | Re-run guest code, import a different manifest, publish or schedule dependent work without receipt |
| `complete`; result receipt committed | Durable receipt bound to lease UUID, manifest digest, and imported result | Return the recorded result; later work gets a fresh lease UUID | Reuse lease/cgroup or re-import changed guest bytes |
| Any phase with cgroup identity/event mismatch or unreadable state | Conflicting/missing cgroup or durable identity | Mark recovery-required; operator repairs only after independently establishing the exact process/cgroup state | PID fallback, automatic identity substitution, candidate import, or dependent work |

An intent is not proof launch occurred. A guest manifest never proves fencing.
The import/result receipt boundary is reconciled by immutable digest; absence of
a receipt after import is an explicit recovery state, not rollback.

## Partial implementation and blocker (2026-11-26; historical pre-amendment state)

After the table above was recorded, focused offline boundary work added:

- `src/sandbox/lease-lifecycle.ts`: a durable per-lease journal with ordered
  transitions, fsynced atomic record replacement, exact cgroup-v2 `cgroup.kill`
  and `populated 0` verification, and reopen recovery that never reads a guest
  fence claim. Its cgroup operations are injectable only through the module
  constructor for in-memory fixture tests.
- `src/sandbox/manifest.ts`: bounded lease-bound file records, path/mode/type
  and digest validation, reserved-path refusal, and case-collision rejection.
- `test/local-sandbox.test.ts`: manifest refusals and durable reopen tests for
  intent-before-launch, launch-before-ack, verified-fence-before-import, and
  import-intent-before-result-receipt. These are in-memory cgroup/journal and
  manifest fixtures only; they do not certify local containment.

Failure-first observations: the first manifest fixture failed on a mismatched
canonical digest; aligning the producer/validator digest format made the focused
suite pass. The first reopen assertion counted the earlier expected cgroup kill
as a recovery kill; comparing the count before and after reopen fixed the test
and retained the no-second-kill assertion.

**BLOCKED — production launcher, fixture rootfs and real certification not
implemented.** The packet requires a fixed stdio helper inside bwrap, but the
existing `src/sandbox/guest-helper.ts` only exports `startGuestHelper({stream,
leaseId,role,cwd})`; it has no standalone entrypoint, stdio stream adapter, or
fixed invocation ABI. The P03 strict paths contain `src/sandbox/local.ts`, but
the spec does not say whether this module is the helper entrypoint or whether
the helper must be a separate trusted asset, and the P01 descriptor deliberately
has no default helper. The required fixture also needs a *pinned* Node runtime,
but neither P03 nor the local matrix specifies a Node version/pin or how the
fixture-builder obtains that trusted runtime. `package.json` only says
`node >=22.19.0`; this is not a reproducible runtime pin. Guessing these
contracts could select an untrusted executable or produce a fixture that does
not match the advertised toolchain.

**Proposed owner:** reviewer/spec owner for M1-P03 should amend the M1-P03
specification (and the §2 toolchain manifest contract if needed) to state the
fixed helper entrypoint and argv/stdio identity, how it is selected from the
existing P01 trust boundary without a fallback, the exact pinned Node version
and digest source, and whether the production importer walks the fenced
workspace or consumes a serialized sealed manifest. Then resume P03 at the
launcher wiring step. No P04/P05 work is authorized by this handoff.
