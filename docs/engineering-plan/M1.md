**Host-boundary amendment (approved 2026-11-25; documentation only).** Step (c)
recorded that the launch/test/lifecycle seams it needed sat outside the strict
list (some callers were listed, but their seams were not). This amendment
authorizes host-boundary wiring only; it does not authorize containment. The
approved decisions are:

- **Fixed defaults + overrides.** On Linux, validate and use
  `process.execPath` for Node, the running operator-selected kit installation's
  own CLI/UI entry points, `/usr/bin/git` and `/usr/bin/gh`. An explicit
  `installation.*` host-profile override replaces the default. There is no
  PATH, target `node_modules/.bin`, cwd-relative, project config/env or `KIT_*`
  authority, and **no fallback after an invalid selected path** (an invalid
  override refuses; it does not try the default). A missing default also
  refuses; it never triggers a PATH search.
- **On demand.** Resolve AND validate a tool at the operation that uses it. An
  unused tool is never resolved: `delivery.mode=none` must not require `gh`,
  and a static command must not require Git, gh, the UI or a sandbox helper.
  An eager all-tool sweep may back an explicit host check, never production
  launch.
- **No-symlink installation trust.** Retain the no-symlink installation-path
  policy and validate both the executable and its ancestor directories
  (canonical, regular/non-symlink leaf, operator/root-owned, not group/world
  writable, outside the target). `process.execPath` is the running process's
  resolved executable path and is validated the same way. The one narrow exception is the **running
  operator-selected dev-in-kit installation**: its own `dist/cli.js`,
  `ui/bin/llm-toolkit-ui.js` and `src/cli.ts`-via-`ui`-tsx entries are trusted
  even when the target is that same checkout. The exception is proven by the
  running entry/installation identity (the resolved module/entry URL), never
  inferred from target cwd, `argv[0]`, a project value or the presence of a kit
  tree in the target. It is limited to the outside-the-target rule: symlink,
  ownership and mode checks still apply. A host whose fixed default is a
  symlink must name the canonical real file in `installation.*`; a symlinked
  default is refused, not silently realpathed.
- **Descriptor injection.** Production builds one host-owned installation
  descriptor from the profile plus fixed defaults. Tests inject an explicit
  descriptor in-process or through private job state; injection is host
  authority, not a validation bypass and not a production-authority source.
  Job launch and attached-stop use the same descriptor/argv identity: the
  runner executes exactly the recorded canonical argv with no re-resolution,
  and attached-stop compares the process argv/executable against that record.
- **Async config.** Read `.orch/config.toml` asynchronously through the
  canonical root, `safe-read` and the pure `parseConfig`; absent, refused and
  malformed remain distinct. **No legacy sync config read counts as packet
  completion**, and no production caller may keep one.
- **Git is more than an absolute path.** Preserve and enforce protections
  against Git-triggered host callbacks and hostile inherited configuration:
  fixed literal argv; a host-built environment with inherited
  `GIT_*`/`GH_*`/`SSH_*`/proxy/`BASH_ENV`/`NODE_OPTIONS` stripped; hooks,
  fsmonitor, external diff/textconv, aliases and smudge/clean filters disabled
  or avoided by plumbing; no repository-controlled executable on the host.
  `gh` is noninteractive, destination-pinned and resolved only for
  `delivery.mode=pr` with `--deliver`.
- **Platforms.** Unsupported-platform operations refuse explicitly (typed
  result) without imposing unnecessary launch prerequisites: on a host where
  the read primitive or a tool default is unavailable, the operation that
  needs it refuses, while commands that perform no project read or host launch
  still run.
- **Boundary.** P01 prepares these host boundaries only. Real gate/probe
  containment (recipe-runner, probes, `[sandbox]` enforcement, leases) remains
  P05 and must consume this resolver rather than adding a second one.

**PR publication destination binding amendment.** `plan` captures the
canonical HTTPS GitHub origin from the exact-root operator
profile before model disclosure when delivery mode is `pr`. The durable plan
and its review mirror record that origin. Grant admission, resume and fresh
wave boundaries require current approval of the same canonical origin.
`publishPullRequest` checks the plan, existing intent and any stacked base
locally before the first remote Git or PR-host call. Each remote call rechecks
current authorization and uses the same literal origin or parsed repository.
Every PR delivery journal state carries the origin from the pre-effect
intent. Stack bases require one latest published parent receipt for the revision, commit
and same explicit destination. Local `none` and `commit` modes need no PR
destination, tools or credentials. PR publication always requires explicit
`--deliver`, including during reconciliation.

| Durable phase | Observation | Allowed action | Forbidden action |
| --- | --- | --- | --- |
| Any PR phase | Plan, intent, parent receipt or current operator authorization is missing, malformed, changed or ambiguous | Report recovery required using local evidence | Any remote call after the refusal |
| Reviewed plan with no delivery intent | Valid bindings and current reviewed controls | Verify the exact remote base and persist the bound pre-push intent | Push or create a PR without durable intent |
| Bound pre-push intent, no push attempt | Exact base and absent head, with current reviewed controls | Record the push attempt, then create the ref with an empty-expected lease | Overwrite, repair or rebase a ref |
| Push may have run | Exact head at the integrated commit | Record confirmation and inspect the exact PR identity | Recreate an absent attempted ref or replace a conflicting ref |
| Head confirmed, PR create unattempted | No matching PR and current reviewed controls | Record the PR-create attempt, then create against the exact base and head | Start a new effect after controls drift |
| PR create may have run | One exact repository/base/head/OID match | Confirm the existing PR | Repeat an uncertain create on missing or conflicting observation |
| Published | Exact ref and recorded PR identity still observable | Return the recorded result | Rewrite completed history, repair effects or use an unbound historical receipt as a stack base |

An unbound legacy pending, failed or unknown intent requires manual recovery.
Keep its journal entries, establish the original destination and effect from
independent operator records, and reconcile outside automated publication.
There is no automatic migration, override or replan that abandons the
unresolved effect. A legacy plan with no unresolved work or effect may be
replaced and reviewed anew. Completed legacy receipts remain available as
history.
